# ADR 0004 TCPの接続拒否を到達性の根拠にする

* 状態 accepted
* 日付 2026-09-07
* 開発段階 M4

## 背景

`network.tcp`はホストへTCP接続を試みます。当初はSSHの22番ポートを使い、
接続に失敗するとネットワークの異常として扱っていました。
疑似クラスタで`sshd`だけを停止すると、次の結果になりました。

```text
ssh        UNAVAILABLE
network    UNAVAILABLE     ← 誤り
```

SSHの停止でネットワークまで異常と判定すると、
ホストへの到達不能と特定サービスの停止を区別できません。

## 決定

到達性のprobeでは、`connection refused`を成功として扱います。
接続拒否の応答があれば、そのアドレスへのパケットが届き、応答が返ったことを確認できます。

特定サービスの稼働確認では、同じ接続拒否を失敗として扱います。
対象サービスが接続を受け付けている必要があるためです。
実装では、到達性を確認する`TcpProbe::reachability()`と、
サービスへの接続を確認する`TcpProbe::new()`を分けています。

## 利点と制限

サービスの停止とホストへの到達不能を独立して観測できます。
これは`SPEC.md` §170・§171・§175の受け入れ要件です。
接続拒否も応答のあった観測として使います。
observationのペイロードに`host_responded`を記録することで、
診断でも接続成功と到達確認を区別できます。

到達性のprobeだけでは、対象ポートのサービスが稼働しているかは判断できません。
firewallがRSTを返す構成では、サービスへ接続できなくても到達可能と判定します。
この場合も、SSHとagentのprobeがそれぞれサービスへの接続失敗を報告します。
接続先のポートは設定で指定し、既定ではSSHのポートを使います。

## 検討した代替案

agentの7444番ポートを使う方法は、agentの停止をネットワークの異常と
誤判定する同じ問題があるため、採用しません。

複数ポートを試し、すべて失敗した場合だけ到達不能とする方法も検討しました。
ホストごとの接続数が増えるため、現時点では接続拒否を根拠にする方法を採用します。
firewallの構成に応じて、将来追加できます。

ICMPは遮断されることが多く、raw socketに権限も必要になるため採用しません。
`SPEC.md` §59でも任意の機能として扱っています。
